Penny — Requirements
====================

The living spec of what Penny must do (Product / Functional) and the
non-negotiable rules it must hold (Technical Invariants / Constraints).

Maintained per the directive in AGENTS.md ("Requirements"): update the
relevant section in the SAME change that alters a behaviour or a constraint.
This file states WHAT and WHY, not HOW.

Penny is a SINGLE-PLAYER, LOCALLY HOSTED product: one user, their own
machine, their own database. The hosted multi-tenant product (auth, billing,
households, tenant isolation, cloud deploy) is a separate private repo —
penny-web — that layers on top of this core via its composition seams. See
docs/superpowers/specs/2026-07-27-single-player-local-first-design.md.


PRODUCT / FUNCTIONAL REQUIREMENTS
---------------------------------

P1. Transaction sync
    Sync bank/card transactions from every connected Plaid item into the
    local database. Sync is re-runnable and idempotent; the immutable Plaid
    record and the derived/analytical record are kept distinct. One item whose
    connection is broken (e.g. an expired login needing re-authentication) must
    not abort the other items' sync or the end-of-run categorization — the
    failure is recorded and reported, not raised. Connections needing
    re-authentication are surfaced to the user: at the top of email reports as
    a plain-text banner, and in chat as an inline Plaid relink card (update
    mode) that restores the existing connection so syncing resumes.

P2. Categorization
    Categorize each transaction with an LLM against the two-level taxonomy.
    Split transactions (e.g. itemized Amazon orders) are categorized per line.

P3. Conversational finance Q&A
    Answer natural-language questions about the user's finances through a
    streaming chat UI, driving the agent over the user's own data.

P4. Scheduled reports & the daemon
    Deliver recurring emailed spending reports, produced by the same agent
    that powers chat and sent via its own email tool over the user's
    configured SMTP. Report jobs are configured as a list in the workspace
    config.toml ([[jobs]]): each names a period (daily / weekly / monthly /
    annual / every_n_days), a calendar slot (New-York local time), its own
    recipient list, and a priority. Scheduling is period-identity based, not
    slot based: a job is due once per occurrence of its period, so a slot
    missed while the machine sleeps still runs later the same period. Of the
    jobs due on one tick, the highest-priority max_emails_per_day send; the
    rest resolve their current period without sending — after an outage only
    the top still-due job fires, never a backfill. A failed send retries on
    the next tick (only success or cap-suppression advances a job's period).
    Scheduled work (sync every N hours plus the report jobs) is run by a
    local daemon (`penny daemon`) installed as a user service at onboarding;
    `penny serve --all-in-one` co-runs it for casual use. Job state (last
    run, outcome, last resolved period) is inspectable via `penny daemon
    status` and the agent's `sync_status` tool. Report recipients come from
    configuration only — per job via [[jobs]] (injected into the job
    subprocess's environment by the daemon) or the PENNY_REPORT_RECIPIENTS
    default — never from the prompt or the model.

P5. Amazon itemization
    Optionally enrich Amazon transactions by scraping order detail so spending
    is attributed per item rather than per lump charge.

P6. Conversation persistence
    Persist conversations and messages so chat history survives across
    sessions: browse history (newest-first) in a drawer, open any past
    conversation, start a new chat.

P6b. URL routing & deep links
    The URL is the source of truth for what's on screen: a conversation lives
    at a deep-linkable /c/<id> URL that a fresh load (re)hydrates; the home
    route always starts a new chat, whose URL becomes the conversation's on
    the first message; unknown routes land home.

P7. Agent workspace
    Maintain a persistent local workspace (~/.penny: memory/, reports/,
    logs/, config.toml, user_id) that carries user state (e.g. budget notes,
    merchant rules) across chat, plugin, and scheduled runs. The workspace is
    a plain directory the user owns; an existing ~/.transactoid is honored.

P8. Output language
    Reports and chat responses are written in English (US) with $ currency,
    regardless of the language of transaction descriptors or memory notes.

P11. Light-only appearance
    The web app renders exclusively in the light "cream" design system on
    every screen. It never follows `prefers-color-scheme: dark` and exposes
    no light/dark toggle.

P12. Progressive agent-embedded onboarding (in-chat)
    A user lands straight in the chat — no wizard in the UI — and the agent
    nudges toward setup steps (connect a bank, tune the taxonomy, add
    merchant rules) at deterministic milestones, naturally and at most once
    per turn, until each step is accepted or dismissed (a dismissed step
    never nudges again but stays revisitable by asking). To connect a bank
    the agent offers an inline Plaid Link card: Plaid runs in the browser and
    the public token is exchanged server-side against the local API, storing
    the linked item and accounts, then kicking off the first sync. Onboarding
    state never appears in the transcript.

P14. CLI onboarding
    `penny init` is the setup front door: a re-runnable interactive wizard
    covering workspace, database URL (auto-detected SQLite/Postgres), model
    key, Plaid credentials, SMTP + recipients, schedule cadence, and daemon
    installation. Answers persist in the workspace config.toml (secrets
    chmod 600) and are loaded by every entrypoint as environment defaults;
    a real environment variable always wins.

P15. Local web app, no accounts
    `penny serve` runs the complete product in one process on
    127.0.0.1:8000 — API plus the built web UI. There are no accounts, no
    sign-in, no landing page. Remote access (e.g. from a phone) is the
    user's network choice: Tailscale is the documented path; a bare ngrok
    URL is warned against. Penny ships no auth layer of its own.

P16. Claude Code plugin (dual surface)
    The same agent is exposed to MCP harnesses via `penny mcp` (stdio):
    toolsets passed through verbatim, with fresh runtime context (date,
    schema, taxonomy, memory) in the MCP initialize instructions, and
    Penny's skills shipped as a Claude Code plugin (plugin/ +
    .claude-plugin/marketplace.json). Plugin and web UI share one database
    (WAL) and one workspace; the daemon keeps both fresh. The plugin never
    spawns services — when the daemon is down, `sync_status` reports
    staleness and the agent suggests `penny daemon start`.

P17. Hosted-data export (transient)
    A one-off tool (backend/transient/single-player-export) exports one
    household from the hosted multi-tenant Postgres into a fresh local
    single-player database, preserving category corrections and history that
    are not re-derivable from Plaid. It reads the source strictly read-only.


TECHNICAL INVARIANTS / CONSTRAINTS
----------------------------------

T1. Host-composition seam (penny-web layering)
    The hosted product composes this core through explicit seams only:
    create_app(AppConfig(auth_dependency, turn_wiring, extra_routers,
    static_dir)) for the web surface, build_agent/build_model for the loop,
    and the PENNY_* env contract for configuration. Core code contains no
    auth, no billing, no tenancy, and no branches on hosting topology.
    Exercised by backend/tests/api/test_app_factory.py until penny-web is
    the real second consumer.

T2a. run_sql is read-only (HARD)
    The agent's run_sql tool accepts only a single read-only SELECT (covering
    VALUES / TABLE / set-ops / WITH … SELECT). It parses every query with
    libpg_query (pglast) and rejects, before execution, any write/DDL/session
    statement, multi-statement input, and side-effecting function call. The
    gate is at the input layer so it holds independently of database grants.
    PENNY_AGENT_READONLY_DATABASE_URL optionally adds a database-level
    read-only role on user-owned Postgres as defense-in-depth. Enforced by
    backend/penny/security/sql_read_guard.py and
    backend/tests/security/test_sql_read_guard.py.

T2b. One schema authority per dialect
    SQLite builds the schema from the models via create_all (bootstrap).
    Postgres is evolved ONLY by the alembic chain (`penny migrate`, run
    automatically by init/serve); create_all is refused there. Migration 029
    (single-player baseline) is the fork point: the hosted DB stays frozen at
    028 + penny-web's overlay chain, and core migrations after the fork must
    NEVER run against the hosted database. Enforced by
    backend/tests/test_schema_authority.py and tests/test_schema_drift.py
    (models must equal the migration chain).

T3. Never point this core at the hosted multi-tenant database
    The single-player core is shaped for a single user's database. The
    hosted (multi-tenant, RLS-constrained) Postgres is off-limits: writes
    would violate its constraints and 029+ would destroy its tenancy. Moving
    data from hosted to local goes through the P17 export tool.

T4. Don't reimplement the libraries
    The agent loop, providers, sessions, sandboxes, skills, and tool
    decorator come from agent-harness; the chat UI components from agent-ui.
    Penny wraps or extends them and never forks their responsibilities.

T5. Config is the only runtime seam
    Cross-environment behaviour reads a PENNY_* variable (config.py /
    os.environ). config.toml supplies defaults via `penny.settings`; the
    environment always wins. Code never reads deploy artifacts.

T6. Local scheduler contract
    Scheduled work runs through `penny daemon` invoking the CLI
    (`penny sync`, `penny run-scheduled-report`) as contained subprocesses;
    jobs are idempotent and skew-tolerant, and a job failure never kills the
    scheduler loop.

T7. Single source of truth
    Prompts live only in backend/.prompts/ (promptorium); taxonomy seed in
    backend/configs/taxonomy.yaml; runtime config in the PENNY_* contract;
    skills in backend/.agent/skills (the plugin symlinks them). No value is
    duplicated across homes.

T8. One database, one user
    Finance and app-bookkeeping tables live in ONE database (the app tables
    namespaced app_*), on SQLite opened in WAL mode so the server, daemon,
    and MCP processes share the file safely. There is no tenant column, no
    request principal, and no row-level scoping anywhere in core: the
    database boundary IS the privacy boundary. The stable local user ref
    (Plaid client_user_id) is a workspace-minted UUID (penny.identity).
    Plaid access tokens are encrypted at rest when PENNY_PLAID_TOKEN_KEY is
    configured (opt-in; the local DB is the user's own).

T9. Verification gate
    `ruff check`, `ruff format --check`, and `pytest` pass before any unit
    of work is considered complete; the frontend builds (`npm run build`)
    and typechecks.

T10. Layered domain architecture (target)
     Code follows the layered stack Types -> Config -> Repo -> Service ->
     Runtime -> UI with forward-only dependencies; cross-cutting concerns
     enter via explicit providers/seams. New code adheres; code a change
     touches migrates toward it under the campfire rule with strict scope
     limits. See AGENTS.md ("Architecture: layered domains").

T13. System-reminder subsystem & onboarding state
     Dynamic onboarding/nudge state never enters the (cache-stable) system
     prompt: it is delivered as server-generated <system-reminder> text
     flushed into the next user message by agent-harness's ReminderQueue and
     drained at run start, hidden from the UI (stripSystemReminders).
     Reminder content is server-generated only. Item status is limited to
     pending/accepted/dismissed; activation is computed deterministically per
     turn, never stored. Enforced by backend/tests/test_reminder_e2e.py,
     tests/test_onboarding.py, tests/test_reminder_queue.py.

T14. Categorizer-eval isolation & signal
     The categorizer eval replays the agent on an in-process, writable
     SQLite snapshot — during the untrusted replay the process-global DB
     points at the snapshot so the agent can never reach the primary. A
     failure records a durable eval_runs row without advancing the
     watermark, and every run emits exactly one status email, so a stopped
     or broken pipeline is never silent. Enforced by
     backend/tests/eval/test_job.py.
